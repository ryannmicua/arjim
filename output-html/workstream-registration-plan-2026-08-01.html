How Arjim learns where each workstream lives

This plan builds point-and-read registration: you point Arjim at a workspace folder, confirm one draft, and Arjim writes a permanent marker file inside that folder — so the folder always knows itself, on any device, even after a clean rebuild.

The big idea in three sentences

Truth lives in the folder

The workspace is its own memory

Arjim writes one small marker, .workstream/workstream.json, into the workstream's own folder. The marker survives Arjim being replaced or rebuilt — the folder always knows what it is.

Device state is disposable

Arjim's local index is just a map

On each device, Arjim keeps a small SQLite index of where workstreams live. It is a replaceable copy: delete it, and a rebuild rediscovers everything from the markers. It never becomes the authority.

You approve every write

Draft → confirm → write → verify

Arjim drafts the marker, you confirm the exact draft, Arjim writes it, then reads it back and revalidates it. Nothing is ever written or deleted without your confirmation.

Registering a new workstream, step by step

The "new folder" flow — the heart of the plan. Arjim never guesses and never overwrites.

If you reject the draft → nothing is written. If the write succeeds but linking fails → the marker still stands, and a later relink reuses its identity.

Where each piece of data lives

The plan's core discipline: durable truth and device-local state never mix.

The marker
.workstream/workstream.json		 Inside the workstream folder Holds identity, label, workspace reference, record homes. Readable by any device or assistant. Durable truth
Local index (SQLite) Private per-user data on this device Routing map: marker → local path. Rebuildable at any time from markers. Replaceable copy
Record homes Real systems and tools (e.g. a task app) Referenced as URIs in the marker. Arjim never opens them, never inspects them for credentials. References only

Already registered? If the folder already holds a valid marker, Arjim simply links it unchanged — no new identity, no confirmation, because nothing is written.

Unregistering — deletion that never surprises

Draft intentBound to the marker's exact identity
→
You confirmExact draft + digest
→
Re-check markerUnchanged? Same identity?
→
DeleteOnly under a cooperative lock
→
Verify absenceRead back; report unregistered
If the marker changed since you looked: Arjim stops, writes nothing, and reports changed-marker-stopped. Re-registration later creates a fresh identity. The small window where another writer could interfere is disclosed as a known limitation — never claimed as a guarantee.

Safety rails baked into the design

Never overwrite

Create-only writes

If anything already occupies the marker path, registration stops with a distinct outcome. No silent replacement, ever.

Identity is permanent

Name is just a label

The identity is a generated UUID stored in the marker. Renaming the label changes nothing about who the workstream is.

Bounded input

Hostile files can't hurt

Markers are capped at 256 KiB, depth 8, and pass strict checks before any schema validation.

No secrets leak

Diagnostics are redacted

URIs, labels, and local paths are never echoed in output, logs, or errors. Record-home URIs are treated as untrusted data.

Access-gated

Only what this device can reach

An instance registers only workspaces it can actually access. Inaccessible ones simply stay unregistered on that device.

Fail closed

Unknown = stop

Invalid, unsupported, or conflicting markers stop for operator resolution. Arjim never "fixes" a marker on its own.
